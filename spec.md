# Specification: Standalone Uniform-Color LED Driver for BeagleBone Green

## 1. Purpose

The Deharrak Clock in Lower Manhattan includes 72 LED panels. Each one-meter-square panel forms an hour or minute digit and contains up to `60 × 26` individually addressable WS2812B or WS2811 pixels, with WS2811 using high-speed data mode. Strings contain up to 300 pixels each and connect to six pins on a BeagleBone Green. A Raspberry Pi commands the panels over Ethernet to form the clock display.

All pixels on a single panel are the same type. A panel's BeagleBone therefore drives either WS2812B strings or WS2811 strings in high-speed data mode; pixel types are never mixed within that panel, its GPIO banks, or its strings.

The installed panels run a version of LEDscape and show occasional display glitches. This project replaces that renderer with a smaller driver focused on the required uniform-color updates.

The driver drives up to six deployed LED strings from the BeagleBone Green using one PRU and the AM335x GPIO `SETDATAOUT` / `CLEARDATAOUT` registers. `dld-init CONFIG_FILE` loads the panel's pixel profile and six string lengths and performs one-time hardware and firmware initialization; subsequent `dld-send color` invocations send a color using that configuration and return only after the final reset period has elapsed. The resident `dld-udp` shim receives the existing LEDscape OPC-over-UDP packets and uses the first RGB pixel as the uniform panel color. Both sending programs link the same internal C sender; the shim does not add a separate firmware or transmission implementation.

The existing hardware is fixed. The six data signals are connected to:

- P8_8
- P8_10
- P8_12
- P8_14
- P8_16
- P8_18

Each data signal feeds a string of up to 300 addressable pixels (`60 × 5`). Each configured length is the exact number of pixels to transmit on that pin; zero disables it. Every enabled string always receives the same requested RGB color. Independent per-pixel and per-string colors are not required.

The utility shall exploit the uniform-color constraint by transmitting one GPIO bank at a time. During a bank pass, every pin that still has pixels to receive changes state together, so each pixel data bit requires only one write to `SETDATAOUT` and one write to `CLEARDATAOUT`. A pin is removed from the active mask after its final configured pixel and remains low while longer strings finish.

This is a diagnostic and operational utility with a required kernel quiet-window helper. Following the user's explicit authorization at approximately 04:00 UTC on 2026-09-06, the ABI4 protected path supersedes the original userspace-only spin. For each nonempty GPIO bank, the helper excludes ARM scheduling and IRQ/FIQ handlers, verifies MMC/EDMA inactivity, pauses CPSW CPDMA, grants that bank to the PRU, and waits using the Cortex-A8 cycle counter without data-memory access in the repeated loop. CPSW and CPU execution are restored between banks. No PRU-to-ARM interrupt is used. Physical qualification remains required; these controls do not establish universal interconnect determinism.

The protected implementation and September 6 bench endurance work are complete. The final run recorded 155,917 successful sends, no failed sends, and no observed waveform violations in 4,452,206,525 complete captured pulses. This is digital header-level evidence with acquisition gaps, not installed-panel qualification. Actual pixel family/color order, downstream electrical behavior, propagation/reset margins, and production startup integration remain open; see the [final bench report](docs/validation-20260906.md) and [review checklist](todo.md).

## 2. Problem being solved

The LEDscape GPIO implementation issues writes to several GPIO peripherals for each pixel bit. The PRU reaches them over the AM335x interconnect rather than through direct PRU `R30` outputs. Contention can vary external-write completion latency, making delayed GPIO edges a mechanism to investigate. September 6 captures found GPIO0 pulse/period violations in the userspace-only replacement, including a 570 ns high for nominal zero data. Those captures do not establish an actual LED decoding/latch error or uniquely identify the source of each delay. The protected implementation addresses the avoidable PRU traffic and the documented ARM/DMA contention sources.

The deployed wiring cannot be changed. The software may be replaced completely.

The proposed first-pass program reduces the traffic generated by the PRU as far as practical:

- one PRU only;
- one GPIO peripheral active at a time;
- exactly two timing-critical GPIO writes per transmitted bit;
- no DDR reads while streaming;
- no shared-memory reads while streaming;
- no second PRU activity;
- no per-pixel framebuffer;
- timing parameters, string counters, the 24-bit color, and the current GPIO mask remain in PRU registers while streaming;
- each pin receives the same 24-bit word exactly as many times as its configured length.

This does not make the GPIO interconnect formally deterministic, but it removes the avoidable interconnect load created by the general-purpose LEDscape renderer.

## 3. Target environment

The first implementation shall target the deployed environment:

```text
Linux beaglebone 3.8.13-bone80 #1 SMP Wed Jun 15 17:03:55 UTC 2016 armv7l GNU/Linux
```

The supplied development board is accessible as `root@beaglebone` over passwordless SSH. Read-only inspection confirmed Debian 7, the `armhf` userspace ABI, GCC 4.6.3, GNU Make 3.81, GNU binutils 2.22, and glibc 2.13 with development headers installed. Use native builds on this board as the first-pass compatibility baseline (§11); the kernel's `armv7l` label alone is not the userspace ABI specification.

Runtime assumptions:

1. The commands run with effective UID zero; the kernel ioctl also requires `CAP_SYS_RAWIO`.
2. `uio_pruss` is available and loaded.
3. No LEDscape, independent OPC renderer, or other noncooperating PRU-control process uses the hardware during the initialized session, including idle time between sends. The test script or production boot setup establishes this prerequisite; DLD does not discover competing services or manage them. The DLD UDP receiver is a cooperating sender under the shared lock.
4. The current device tree already pinmuxes the six header pins as GPIOs.
5. The six signals are electrically compatible with the existing deployed level-shifting and LED hardware.
6. PRU0 is used for output. PRU1 remains disabled from initialization through all subsequent sends, including idle time between commands.
7. The operator runs `dld-init CONFIG_FILE` successfully before sending colors and reruns it after reboot, PRUSS reset, or a driver failure requiring recovery. The send path trusts this prerequisite and does not independently verify firmware identity or liveness.
8. The matching `dld_quiet.ko` module is loaded and `/dev/dld-quiet` is available. Only CPU0 is online, its minimum/maximum/current frequency is fixed at 1 GHz, and the helper can reserve an exclusive, pinned hardware cycle counter.
9. The reference appliance uses the matching kernel's `CONFIG_MUSB_PIO_ONLY=y`; USB host/gadget configuration is left intact. There is no swap, and no active unaccounted autonomous DMA client. Recorded bench preparation sets the CPU policy and disables the four user-LED triggers reversibly; runtime binaries and logs use `tmpfs`. See [quiet-window operation](docs/quiet-window.md) for checks and limits.

Initialization and both senders shall use the same exclusive lock and fail rather than overlap another cooperating initialization or send. The resident receiver takes and releases this lock per frame, retaining only its file descriptor between frames. This lock coordinates cooperating `dld` commands only; it does not exclude LEDscape or other software that ignores it.

## 4. Command-line interface

### 4.1 Invocations and lifecycle

```text
dld-init CONFIG_FILE
dld-send color
dld-udp [--bind ADDRESS] [--port PORT] [--no-startup-flash] [--no-idle-flash]
```

Example:

```sh
sudo ./dld-init /etc/dld.json
sudo ./dld-send FF8000
sudo ./dld-send 0000FF
```

With the example configuration below, this initializes all six data pins as outputs driven low, enables all six strings at length 300, then sends RGB color `#FF8000` followed by `#0000FF` to those strings.

`dld-init` shall read and validate the configuration file, configure **all six pins as outputs, including zero-length pins**, set all six output levels low, store the selected pixel profile and six lengths in PRU0 local data RAM, load and start PRU0, and perform all other one-time initialization. It shall return only when the firmware is ready to accept a color. Initialization sends no pixel data and preserves previously latched colors when the display is healthy and idle. After an interrupted transmission, forcing the data lines low can latch pending data; initialization or recovery does not guarantee preservation of the previous display in that case.

`dld-send` shall accept only a color, use the profile and lengths established by the most recent successful `dld-init`, and wait until every configured pixel has had sufficient time to latch that frame's color. The final wait includes the selected profile's reset duration, a conservative allowance for propagation through the configured strings, and a safety margin as specified in §6. A normal send shall not reread the configuration file, change the profile or lengths, reconfigure GPIO directions, reload or restart the PRU, or repeat one-time hardware initialization. Critical failure uses the separate cleanup path in §9.6.

The configuration and running PRU firmware shall survive the exit of the commands. The local CLI path requires no resident host daemon; UDP reception uses the optional resident `dld-udp` process. Initialization remains valid until reinitialization takes control of the hardware, a reboot, PRUSS reset or loss of its configuration, or an execution failure that invalidates the initialized state. Once reinitialization takes control, a failed `dld-init` leaves the driver uninitialized. Successful initialization is an operator prerequisite. Both senders retain basic command-block and readiness checks (§8.3), but do not independently prove that initialization occurred or the firmware is still running. Neither shall initialize implicitly.

A previous request still in progress is temporarily not ready for another send; it does not by itself invalidate initialization. A new `dld-send` shall fail before publication without disturbing that request. Once the PRU finishes and the existing validity/readiness checks pass, a later invocation may send normally, even if the previous host process died before observing completion.

Run `dld-init` again to apply changes to the configuration file or recover from an invalidated state. Reinitialization shall acquire the same lock, clear all six outputs low, and replace the previous configuration. Editing the file alone does not affect a running session. Each one-shot command requires exactly one argument; the UDP receiver's options are defined in §4.5. Stop the receiver before operator-driven reinitialization and restart it after success.

### 4.2 `color` (`dld-send`)

`color` is an RGB value in conventional `RRGGBB` order.

Accepted forms:

```text
RRGGBB
0xRRGGBB
0XRRGGBB
```

Rules:

- Exactly six hexadecimal digits are required after an optional `0x` or `0X` prefix.
- Hexadecimal digits are case-insensitive.
- No leading `#` is accepted because `#` has shell-comment semantics.
- The host converts RGB input to the selected pixel profile's wire color order before submitting the send request to the already running PRU.
- The most-significant wire bit is transmitted first.

Example conversion for a profile whose wire order is GRB:

```c
r = (rgb >> 16) & 0xff;
g = (rgb >>  8) & 0xff;
b =  rgb        & 0xff;

wire_color = (g << 16) | (r << 8) | b;
```

### 4.3 Panel configuration (`dld-init`)

`CONFIG_FILE` names a local JSON file. The file shall contain exactly these required fields:

```json
{
  "pixel_type": "ws2812b",
  "string_lengths": [300, 300, 300, 300, 300, 300]
}
```

`pixel_type` selects a named pixel profile from the catalog supplied with the host tools, kernel helper, and embedded firmware. A profile defines its intended pixel family/variant, wire color order, symbol timing, reset duration, propagation allowance per pixel, and final-wait safety margin. The initial catalog has these four profiles:

| Profile name | ABI identifier | Wire byte order |
|---|---:|---|
| `ws2812b` | 1 | GRB |
| `ws2811-hs` | 2 | RGB |
| `ws2812b-bgr` | 3 | BGR |
| `ws2811-hs-bgr` | 4 | BGR |

All four use the initial symbol timings in §7.1, a 300 µs base reset, a 1 µs allowance per forwarding pixel, and a 100 µs positive margin. These propagation/margin values are engineering allowances, not measured maxima for installed LEDs. Keep distinct variants named separately; the current catalog has no GBR profile. Validate the actual timing and color-order mapping on deployed hardware before treating any profile as production-qualified.

Each panel currently has a local LEDscape color-order configuration. Use that known configuration and measurements when assigning its new profile. The new panel file stores the profile identifier; it does not expose separate color-order overrides or arbitrary nanosecond timing inputs.

The earlier reference BBG's LEDscape configuration specifies BGR, which motivated the BGR variants. The replacement September 6 waveform-bench BBG instead specifies GBR and 100 pixels per string. Neither configuration identifies the precise pixel family or proves the physical color order. Black/white diagnostics are byte-order independent; colored wire-pattern tests do not substitute for checking the installed LEDs.

`string_lengths` shall contain exactly six JSON integers in the range 0 through 300 inclusive. Their array order is the physical header-pin order below, independent of GPIO bank pass order:

| Array index | Header pin | AM335x GPIO | Global GPIO number |
|---:|---|---|---:|
| 0 | P8_8  | GPIO2[3]  | 67 |
| 1 | P8_10 | GPIO2[4]  | 68 |
| 2 | P8_12 | GPIO1[12] | 44 |
| 3 | P8_14 | GPIO0[26] | 26 |
| 4 | P8_16 | GPIO1[14] | 46 |
| 5 | P8_18 | GPIO2[1]  | 65 |

Examples:

```text
[300, 300, 300, 300, 300, 300]  all six strings, 300 pixels each
[300,   0,   0,   0,   0,   0]  P8_8 only
[300, 180,   0,   0,   0,   0]  P8_8 has 300 pixels; P8_10 has 180
[  0,   0,   0,   0,   0,   0]  all strings disabled; initialize and remain ready
```

Reject malformed JSON, missing/duplicate/unknown fields, unknown profile names, wrong value types, incorrect array length, and out-of-range lengths before touching hardware. The entire file shall be read into a validated snapshot before initialization begins. The configuration file persists across process exits and reboots; the initialized copy in PRU RAM has the session lifetime described in §8.3.

An enabled string receives the requested color on each `dld-send`. A disabled pin remains configured as an output and is held low during initialization, sends, and idle time; its string receives no new data from these commands. A healthy, idle disabled string retains its previously latched color. If a previous transmission was interrupted, establishing the low/reset level may latch pending data as described in §4.1, so preservation of the prior picture is not guaranteed. Turning a newly disabled string black is outside the first-pass scope and is covered under **Future work**.

With all six lengths zero, `dld-send` shall send no pixel data, keep all six outputs low, and still perform the final wait defined in §6, using zero chain-propagation delay, before returning success. No separate enable mask is configured or stored; a string is enabled exactly when its length is nonzero.

### 4.4 Output and exit status

On successful initialization, `dld-init` shall print one line:

```text
OK pixel_type=PROFILE lengths=L0,L1,L2,L3,L4,L5 groups=N
```

On successful frame completion, `dld-send` shall print one line:

```text
OK color=RRGGBB quiet_cycles=C2,C1,C0 dma_cycles=D2,D1,D0 pixel_type=PROFILE lengths=L0,L1,L2,L3,L4,L5 groups=N
```

`N` is the number of GPIO banks containing at least one nonzero configured length. Lengths use the array order above. Send diagnostics report measured IRQ-off and CPSW-drain cycles in GPIO2, GPIO1, GPIO0 order; empty banks report zero. These are host diagnostics, not physical GPIO-edge measurements. Errors go to standard error.

Exit codes:

| Code | Meaning |
|---:|---|
| 0 | Success, including normal idle UDP receiver termination |
| 2 | Invalid command-line syntax, color, or configuration content |
| 3 | Missing privilege/runtime prerequisite, unreadable configuration, or UDP socket error |
| 4 | PRU initialization, loading, or readiness failure |
| 5 | Critical send-completion failure or PRU-reported error |
| 6 | Shared command lock is held or an outstanding PRU request prevents a new command |
| 7 | Initialized command block is missing, incompatible, or invalid; run `dld-init` |

### 4.5 LEDscape UDP shim (`dld-udp`)

The receiver shall run in the foreground after successful initialization. It shall accept optional `--bind ADDRESS` and `--port PORT`, independent `--no-startup-flash` and `--no-idle-flash` flags, plus `--help`. Addresses are numeric IPv4 or IPv6 literals; ports are decimal integers 1 through 65535. Defaults are `::` and port 7890, explicitly permitting IPv4 reception on the IPv6 socket. An explicit IPv4 wildcard supports IPv4 unicast and broadcast through the existing network configuration. Binding is exclusive, without socket reuse. The receiver shall not change network or service configuration.

Interpret each UDP datagram as the first OPC message below:

| Offset | Field | Rule |
|---:|---|---|
| 0 | Channel | Accept any value; ignore it |
| 1 | Command | Accept zero (set pixel colors) only |
| 2–3 | Payload length | Unsigned big-endian byte count, at least 3 |
| 4–6 | First pixel | Logical red, green, blue bytes |
| 7 onward | Remaining data | Require the complete declared payload; ignore later pixels |

Reject short headers, unsupported commands, payloads shorter than one RGB pixel, and truncated declared payloads without invoking the sender. Ignore bytes after the first complete declared message, including any subsequent OPC messages; do not require the payload length to be a multiple of three. Wire order comes exclusively from the initialized local profile. No pixel type, string lengths, waveform parameters, or independent output colors can be changed through the packet.

After receiving a datagram, drain a bounded batch of up to 64 datagrams total without blocking and send the newest valid color in that batch. Invalid input does not overwrite an already selected valid color. A batch containing no valid packet submits no frame. Keep only one selected color, with no separate application frame queue. A larger socket backlog can take several batches; this is not an unbounded drain to the globally newest datagram. Repeated identical colors shall be sent again. With no packet sequence field, selection follows receive order across all senders; stale or reordered network traffic cannot be identified.

Wait for full completion of the selected frame before receiving the next batch. There is no per-packet configuration-file read, fork, device reopen, or PRU remap. The shared sender shall retain its PRU mapping, kernel device descriptor, and lock descriptor for the process lifetime, acquire/release the shared lock per frame, and validate the current mailbox/profile/lengths on every send. A successful intervening coordinated initialization therefore cannot leave a cached profile in use. Keep the kernel/firmware ABI and protected timing unchanged.

The receiver shall discard malformed or unsupported packets and continue; any sender failure, including busy or invalid session, terminates it with the existing send exit code and no automatic initialization or frame retry. Socket/runtime failures use exit 3 and invalid options use exit 2. Normal startup and exit diagnostics, including local counters, go to stderr; do not log every successful frame or write normal output to stdout. Idle `SIGINT`, `SIGTERM`, or `SIGHUP` stops normally with exit 0 and sends no blackout frame. Once a send starts, its existing cancellation/critical failure contract applies (§9.6).

Two status flashes are enabled by default. After successful socket binding and shared-sender attachment, run a one-time green (`00FF00`) flash unless `--no-startup-flash` is set. After more than 60 seconds since the latest successfully received datagram or completion of the previous red flash, run a red (`FF0000`) flash unless `--no-idle-flash` is set. Begin the first inactivity interval at successful sender attachment; completing green does not reset it. Every datagram read from this bound socket counts as activity, including malformed or unsupported OPC messages; this is not a timer since the last successful color update. Lost or unread packets do not reset it.

A smooth flash starts black, ramps linearly in its RGB channel value from zero to 255 over 0.5 seconds, and immediately ramps back to black over another 0.5 seconds. Send every animation frame synchronously through the existing shared sender. Anchor monotonic elapsed time immediately before sending initial black. After completion including final reset, compute the next intermediate color from elapsed time; do not use a fixed frame count, fixed frame rate, or an inter-frame delay. Explicitly submit initial black, full primary color at the first available opportunity at or after the 0.5-second boundary, and final black at or after the one-second boundary. The one-second boundary remains relative to the initial anchor, without restarting at the peak. Even if a slow send passes both boundaries, send full primary before final black unless interrupted by valid input. Slow sends may skip intermediate levels and extend completion beyond the nominal duration; no endpoint requires an overlapping send or a separate transmission implementation.

Check incoming datagrams before the first flash frame and between subsequent frames, using the normal bounded batch policy. A valid color packet interrupts either flash and its selected color is sent next; a startup flash never restarts and can be superseded before it emits any frame. Invalid packets reset inactivity but do not replace the selected color or interrupt an in-progress flash. Do not abort an in-flight send to process traffic. An uninterrupted flash ends black without restoring the previous packet color. Handled shutdown between frames sends no additional frame, so an intermediate color may remain. The usual sender failure/cancellation contract applies to flash frames as well as packet frames. Neither flash changes `dld-send` or `dld-init` behavior.

Keep `sent` as the count of successfully completed packet-derived frames. Report completed animation frames separately as `flash_frames`, completed green/red cycles as `startup_flashes`/`idle_flashes`, and valid-packet takeovers as `interrupted_flashes`. Count a completed flash only after its final black frame succeeds; signal cancellation is not a packet interruption.

Emit the exact line `dld-udp: ready` on stderr once startup succeeds. With the startup flash enabled, emit it only after the final black frame completes or after a valid packet supersedes the flash and its selected color sends successfully. With `--no-startup-flash`, emit it after successful socket binding and sender attachment, without an added test frame. Do not treat the earlier listening diagnostic as successful flash completion. This line is a one-time startup notification, not an ongoing health monitor or acknowledgment for later packets. The external [temporary SSH deployment](docs/trial.md) waits up to 20 seconds for it; that deadline belongs to the launcher, not the receiver's transmission contract.

The shim provides no acknowledgment, packet sequence, duplicate suppression, automatic retransmission, TCP listener, or transform of incoming RGB values. Apart from these two status flashes, it has no general animation, gamma correction, dithering, or interpolation engine. With `--no-idle-flash`, normal packet silence preserves the last completed color. Local receive/send counters cannot account for packets dropped before reaching the socket. A 20 Hz source is a workload to test, not a guaranteed 50 ms receive-to-completion deadline. See [UDP operation](docs/udp.md) for setup and packet examples; a possible future reliable protocol remains separate (§14.4).

## 5. GPIO mapping and sequential groups

The six signals occupy three GPIO banks.

### 5.1 Register addresses

```c
#define GPIO0_BASE          0x44E07000u
#define GPIO1_BASE          0x4804C000u
#define GPIO2_BASE          0x481AC000u

#define GPIO_OE             0x134u
#define GPIO_DATAOUT        0x13Cu
#define GPIO_CLEARDATAOUT   0x190u
#define GPIO_SETDATAOUT     0x194u
```

`SETDATAOUT` and `CLEARDATAOUT` are used so unrelated GPIO output bits in each bank are never modified. Writing a one affects the selected bit; writing a zero has no effect.

### 5.2 Fixed LED masks

```c
#define GPIO2_LED_BITS  ((1u << 1) | (1u << 3) | (1u << 4))
#define GPIO1_LED_BITS  ((1u << 12) | (1u << 14))
#define GPIO0_LED_BITS  (1u << 26)
```

### 5.3 Runtime group masks and lengths

Given array `lengths[6]` established by `dld-init` in the order defined in §4.3, the initial masks are:

```c
gpio2_mask =
    ((lengths[5] > 0) ? (1u << 1) : 0) |  /* P8_18 */
    ((lengths[0] > 0) ? (1u << 3) : 0) |  /* P8_8  */
    ((lengths[1] > 0) ? (1u << 4) : 0);   /* P8_10 */

gpio1_mask =
    ((lengths[2] > 0) ? (1u << 12) : 0) | /* P8_12 */
    ((lengths[4] > 0) ? (1u << 14) : 0);  /* P8_16 */

gpio0_mask =
    ((lengths[3] > 0) ? (1u << 26) : 0);  /* P8_14 */
```

The bank lengths are `max(lengths[0], lengths[1], lengths[5])` for GPIO2, `max(lengths[2], lengths[4])` for GPIO1, and `lengths[3]` for GPIO0. These masks and bank lengths are derived working values, not independent configuration.

Within each pass, remove a pin from the active mask immediately after the final CLEAR of its last configured pixel. Mask changes occur only between complete pixels and require no extra GPIO writes. Reload the original lengths and initial masks for each new frame; do not decrement or otherwise overwrite the persistent configuration.

### 5.4 Required pass order

The PRU shall transmit nonempty groups in this fixed order:

1. GPIO2: P8_8, P8_10, P8_18
2. GPIO1: P8_12, P8_16
3. GPIO0: P8_14

A group whose initial mask is zero shall be skipped completely. No SET, CLEAR, or empty-mask timing loop shall be issued for a skipped group during a send. Initialization and error cleanup still establish all six outputs low.

The order is fixed to make captures, logs, and kernel bank grants reproducible. The application accepts the resulting update skew between GPIO banks; simultaneous updating of all six strings is not required.

## 6. Pixel and frame behavior

For a pin with configured length `L`, the PRU shall transmit exactly:

```text
L pixels × 24 bits per pixel = 24 × L data bits
```

The same 24-bit profile-ordered color is sent for every pixel. A bank uses `24 × max(bank lengths)` bit slots, with shorter strings dropping out after their last pixel. Zero-length pins never pulse. There is no padding of shorter configured lengths to the bank maximum.

For example, with P8_8 length 300, P8_10 length 180, and P8_18 length zero, the first 180 GPIO2 pixel words go to P8_8 and P8_10 together. P8_10 then remains low while P8_8 receives another 120 words.

Consequences:

- Pixels 0 through `L - 1` on each enabled string receive the requested color.
- Configuration shall match the intended addressable pixel count; the driver does not discover physical lengths. A mismatch is a configuration error, and the driver makes no guarantee about pixels beyond the configured length.
- Physical strings longer than 300 addressable pixels are outside the first-pass supported scope.
- A finished string stays low and can latch while longer strings in its bank, or subsequent banks, are still transmitting. The application accepts this update skew, including earlier updates on shorter strings within a bank. Do not pad strings or add delays to synchronize their latching; the final completion guarantee in §6.1 still covers every configured pixel.

### 6.1 Final reset and completion guarantee

Successful completion means every configured pixel has had sufficient time to latch the requested color. This is a timing guarantee for correctly configured, supported hardware; the one-way LED interface provides no readback acknowledgment from the pixels.

After the final nonempty bank's end-of-group clear/readback succeeds (§7.5), keep all six outputs low for at least:

```text
Lmax    = maximum of all six configured string lengths
Treset  = max(300 µs, selected profile's required reset-low duration)
Tchain  = max(Lmax - 1, 0) × selected profile's maximum per-pixel propagation delay
Tsettle = Treset + Tchain + selected profile's safety margin
```

Use the longest configured string across all banks, even if it is not in the final bank. This conservative calculation avoids needing to track a separate completion deadline for each string. Earlier strings remain low while later strings transmit, so one final `Tsettle` wait covers them as well.

The per-pixel propagation bound shall cover forwarding of the final falling edge. The profile's positive safety margin shall cover any remaining delay from successful GPIO clear/readback to that falling edge reaching the first pixel's DIN, including output-latch-to-pad delay, level shifting, and wiring, plus clock/timing uncertainty and any additional allowance needed by the supported hardware. A datasheet's strict greater-than reset requirement must be satisfied, not merely equaled. Round the implemented wait upward to PRU cycles and account for loop/setup instructions so it cannot finish early. Profile-specific bounds and margins require validation during the hardware testing recorded under review item 7; typical propagation values are not sufficient for the bound.

Do not start the PRU's final wait at the issue of a posted GPIO CLEAR. Start it only after the last bank's successful clear/readback, then publish `DONE` after the entire wait. No completion interrupt is raised. The kernel helper must observe that matching completion through bounded, IRQ-enabled final polling before `dld-send` prints success or exits successfully. All six outputs remain low between requests.

When all six lengths are zero, use `Tchain = 0` and wait `Treset + safety margin` from request acceptance. No pixel-data writes or bank passes are required.

## 7. Pixel waveform and timing profiles

### 7.1 Profile selection and nominal resolution

One static firmware image shall support the supplied pixel profiles. `dld-init` selects the profile once; choosing a supported profile or changing string lengths does not require a different firmware build. Host and PRU code shall share a versioned definition of profile identifiers and parameters.

Each profile defines the wire byte order, nominal bit period, zero/one high times, reset-low duration, maximum per-pixel propagation delay, and safety margin used by §6.1. Compute the configuration's `Tsettle` before streaming. Express firmware timing parameters in PRU cycles and load them into registers before timed transmission. No per-bit memory reads, profile lookups, or conversions from nanoseconds are allowed. Separate hardcoded waveform routines are optional; register-loaded delay counts are permitted.

At the assumed 200 MHz PRU clock, nominal timing shall be adjustable in 5 ns instruction-cycle steps. A two-instruction decrement/branch delay loop alone advances in 10 ns steps; use a fully accounted extra-cycle path where needed to retain 5 ns resolution. Account for every setup, copy, branch, GPIO-write issue, and pixel-boundary instruction. This specifies the nominal issue schedule, not 5 ns accuracy at the physical LED input.

Reject unsupported profiles or parameters that cannot meet their specified timing after all required bookkeeping. The panel configuration does not accept arbitrary timing values. Use the following agreed initial symbol timings for both `ws2812b` and `ws2811-hs`, and adjust the built-in profile parameters as needed during hardware testing. Host and firmware definitions must remain compatible under §8.3.

The bit period is the time from one data bit's rising edge to the next data bit's rising edge: `Tbit = TH + TL`. Maintain that period between consecutive data bits on each still-active pin, including across pixel boundaries within a bank pass.

| Parameter | Initial target for both types | PRU cycles at 200 MHz |
|---|---:|---:|
| Bit period (`Tbit`), rising edge to rising edge | 1,200 ns | 240 |
| Zero-symbol high time (`T0H`) | 350 ns | 70 |
| Zero-symbol low time (`T0L`) | 850 ns | 170 |
| One-symbol high time (`T1H`) | 700 ns | 140 |
| One-symbol low time (`T1L`) | 500 ns | 100 |

The base reset floor remains 300 µs. The complete final wait remains `Tsettle = Treset + Tchain + safety margin` as defined in §6.1; adopting common symbol timings does not merge the profiles' reset, propagation, margin, or wire-order definitions.

The initial nominal issue-point schedule is:

```text
SET issue                         cycle 0
CLEAR issue for a zero            cycle 70
CLEAR issue for a one             cycle 140
next bit's SET issue              cycle 240
```

These are accepted starting targets for this iteration, not a claim of compliance with every pixel revision. For example, the referenced [WS2812B-V5 datasheet](https://www.world-semi.co.kr/_files/ugd/89cd03_1023b0e9d135431aa1e6491bfc318112.pdf) prints a 580 ns minimum `T1L`, above this baseline's 500 ns; the older [WS2811 datasheet](https://www.mouser.com/datasheet/3/1348/1/WS2811.pdf) also describes different nominal high-speed timings. Verify behavior on the installed strings and adjust profiles as required.

Because GPIO writes cross the AM335x interconnect, distinguish the nominal issue schedule from measured edge timing. The completed diagnostic header captures used ±50 ns timing limits. Across both protected overnight runs, measured rising periods were 1,206–1,214 ns, retaining an approximately 10 ns bias from the nominal 1,200 ns schedule; its cause is not established and the firmware was not tuned to remove it. These measured limits do not establish universal LED compliance. Installed-panel qualification still requires first-pixel DIN measurements after level shifting/wiring, header comparisons, profile reset/propagation bounds, and safety margins (§13.4).

### 7.2 Two-write symbol generation

Each bit shall use exactly two external GPIO writes:

```text
write active_mask to GPIOx_SETDATAOUT
wait zero-high or one-high interval
write the same active_mask to GPIOx_CLEARDATAOUT
wait until the selected profile's bit period is complete
```

No redundant SET writes are permitted.

No mid-symbol zero-mask write is permitted.

No write to another GPIO peripheral is permitted during a group pass.

### 7.3 Runtime bit selection

The wire color is a runtime value, but the 24 bit positions shall be statically unrolled in the PRU source:

```text
send bit 23
send bit 22
...
send bit 1
send bit 0
```

Each unrolled bit macro tests a fixed immediate bit number before issuing SET, then follows either a zero path or one path. Both paths must have an exactly accounted total duration equal to the selected profile's bit-period cycles between successive SET issue points; the initial 1,200 ns timing uses 240 cycles.

The outer pixel loop runs until the longest configured string in the bank finishes. Include the instructions that update counters, compare individual string endpoints, shrink the active mask, and branch the pixel loop in the low-time accounting for bit 0. With the initial targets, the shortest such interval is the 100-cycle low period after a one bit. Balance all paths so remaining strings begin the next pixel on schedule, including when one or more neighboring strings finish. The mask used for a bit's SET and CLEAR must be identical; it may shrink only after the CLEAR of bit 0.

The implementation shall be verified from the final assembler listing, not solely from source-level assumptions.

### 7.4 No external access inside the timed loop

From the first SET of a group until its final CLEAR, the PRU shall not perform any of the following:

- DDR reads or writes;
- shared PRU RAM reads or writes;
- host-command reads;
- GPIO status reads;
- cycle-counter MMIO reads;
- writes to a different GPIO bank;
- PRU-to-ARM interrupts;
- PRU1 communication.

Only these state elements may be used during the timed loop:

- PRU registers;
- deterministic PRU instructions;
- one group's `SETDATAOUT` address;
- one group's `CLEARDATAOUT` address;
- one group's active mask, changed only between pixels;
- the current group's configured lengths and working counters held in registers;
- the selected profile's timing parameters and working delay counters held in registers.

### 7.5 End-of-group drain

After the final data-bit CLEAR for a group:

1. Write the complete fixed LED mask for that bank to `CLEARDATAOUT`, ensuring even disabled LED outputs are low.
2. Read `GPIO_DATAOUT` for the same bank.
3. If any fixed LED-mask bit remains high, retry the clear/read operation up to eight total attempts (`DLD_DRAIN_ATTEMPTS`). An instruction/attempt cap does not bound an external bus transaction that never completes.
4. Do not perform this read inside the timed bank stream.

This readback is not used to time symbols. It is only an end-of-group completion/drain check.

## 8. PRU firmware requirements

### 8.1 PRU selection

- Use PRU0 only.
- Explicitly disable PRU1 before PRU0 starts.
- Do not load a no-op program onto PRU1; leave it disabled.

### 8.2 Initialization and request loop

When loaded by `dld-init`, the PRU firmware shall:

1. Enable its OCP master port by clearing `STANDBY_INIT` in PRUSS configuration.
2. Load and validate magic, ABI version, built-in profile, and six lengths from PRU0 local data RAM.
3. Derive bank masks and timing parameters without modifying persistent configuration.
4. Verify all six LED GPIO bits are outputs. Report an error rather than changing `GPIO_OE` in firmware.
5. Clear/read back all six outputs with a finite bound, then hold them low for `Tsettle` (§6.1).
6. Publish `READY`, with sequence and bank-handshake fields zero, and wait for requests. Raise no readiness interrupt.

For each send request, the firmware shall:

1. Accept a new sequence, clear previous bank-handshake outputs, publish `accepted_seq`, and load its wire color before entering any bank gate. Equality comparisons permit sequence wraparound with one outstanding request.
2. For each nonempty bank in GPIO2, GPIO1, GPIO0 order, preload its color, timing, counters, and mask into registers. Publish `WAIT_BANK` followed by the fixed ordinal in `bank_ready`, and wait for matching `bank_grant`. Skip empty banks without renumbering.
3. Issue no pixel-data edge before that grant. After the grant, clear `bank_ready`, publish `RUNNING`, and transmit exact configured lengths without command-block access inside the timed bit stream.
4. Perform the end-of-bank clear/readback, then publish its ordinal in `bank_done`. A later bank must await its own grant even if the previous bank completed early. Gate protocol errors publish `ERROR`.
5. After the final successful clear/readback, hold low for `Tsettle`. With all lengths zero, begin that hold from acceptance and require no bank grant.
6. Leave `bank_ready` zero, publish matching `completion_seq` and error detail, then publish `DONE`. Return to the request loop without halting or changing configuration. Raise no completion interrupt.

Mailbox polling is permitted while idle or waiting for a grant, never during pixel transmission. A failed clear, invalid gate, or other firmware error remains observable and requires reinitialization. The PRU never alters GPIO direction or output bits unrelated to the six LED signals.

### 8.3 Required PRU command block

Reserve this word-aligned, **72-byte ABI4** block at offset zero in PRU0's 8 KB local data RAM: PRU address `0x00000000`, ARM physical address `0x4A300000`. It is hardware RAM, not a process allocation. UIO mappings and the kernel device mapping refer to the same storage; releasing a mapping does not clear it. The separate PRUSS shared-RAM region is unused.

```c
#define DLD_COMMAND_MAGIC 0x444C4431u
#define DLD_ABI_VERSION   4u

struct dld_command {
    uint32_t magic;             /* offset 0 */
    uint32_t abi_version;       /* 4 */
    uint32_t profile_id;        /* 8: init owns configuration */
    uint32_t string_lengths[6]; /* 12..35: physical header order */
    uint32_t wire_color;        /* 36: kernel writes profile-ordered RGB */
    uint32_t request_seq;       /* 40: kernel publishes request last */
    uint32_t completion_seq;    /* 44: PRU completes after Tsettle */
    uint32_t status;            /* 48 */
    uint32_t error_detail;      /* 52 */
    uint32_t bank_ready;        /* 56: PRU's requested bank ordinal */
    uint32_t bank_grant;        /* 60: kernel's authorized bank ordinal */
    uint32_t bank_done;         /* 64: PRU's completed bank ordinal */
    uint32_t accepted_seq;      /* 68: PRU's accepted request sequence */
};
```

Statuses are `INITIALIZING=0`, `READY=1`, `RUNNING=2`, `DONE=3`, `WAIT_BANK=4`, and `ERROR=0x80000000`. Bank ordinals are `GPIO2=1`, `GPIO1=2`, `GPIO0=3`; zero means no bank. Error codes distinguish invalid magic, ABI, profile, length, timing, GPIO direction, initialization clear, bank clear, internal state, and gate protocol.

`dld-init` zeros all sequence/gate fields and sets `INITIALIZING`. A ready session has compatible magic/ABI, supported profile/lengths, no error, matching request/completion sequences, and `READY` or `DONE`. `READY` requires zero sequence/handshake fields. For `DONE`, `accepted_seq` matches the request, `bank_ready` is zero, and grant/done equal the last nonempty bank ordinal (zero when all disabled). `RUNNING`, `WAIT_BANK`, or an outstanding sequence is busy. Sequence inequality must reject an earlier publication even before the PRU replaces an old status.

These are compatibility/readiness checks, not independent firmware identity/liveness verification. Do not add image hashes, heartbeat/probe requests, or ordinary-send PRU run-state checks. A stopped PRU with a valid ready mailbox permits publication but cannot reach the next gate or completion; that bounded wait fails critically. A retained busy mailbox is rejected before publication even if its PRU is stopped. Missing/incompatible/invalid state gives exit 7; an intact busy state gives exit 6. Kernel clock checks protect MMIO access and are separate from firmware-liveness checks.

Initialization owns profile and lengths. The kernel, acting for the shared sender used by `dld-send` and `dld-udp`, owns `wire_color`, `request_seq`, and `bank_grant`; the PRU owns `accepted_seq`, `bank_ready`, `bank_done`, `completion_seq`, status, and error after initialization. Clear the old grant and publish color before the new request sequence, with ARM device-memory ordering and a completed publication barrier. A new request cannot reuse stale grant/done state. Grant only after observing matching `accepted_seq`, `WAIT_BANK`, and `bank_ready` and establishing that bank's quiet window.

The catalog and handshake semantics must agree across loader, firmware, host, and module. Changing a profile identifier's meaning or mailbox semantics requires an ABI change. Do not mix old ABI3 firmware/userspace senders with ABI4; there is no userspace-only fallback.

Volatile configuration/firmware survive successful command exits. The kernel continues a submitted finite request even if its sender receives a fatal signal, including remaining grants and final completion. Any submitted failure invokes kernel-owned cleanup, independent of userspace survival. Successful completion after sender death leaves a reusable session. Reboot, reset, reinitialization, and failed-request cleanup invalidate it. There is no separate orphan flag or recovery protocol.

Bank success requires `bank_done == expected ordinal` at the single post-spin read. Overall success additionally requires `DONE`, matching accepted/completion sequences, and no error after all of `Tsettle`. Elapsed CPU time is never proof of PRU completion. Use uncached/device mappings and explicit ordering; `volatile` alone is insufficient.

### 9.3 `dld-init` sequence

The initialization command shall:

1. Parse its single `CONFIG_FILE` argument, read the entire file, and fully validate the JSON schema, profile selection, and six lengths before touching hardware.
2. Acquire a nonblocking exclusive lock, such as `/var/lock/dld.lock`.
3. Confirm effective UID zero.
4. Initialize the included loader and open the UIO device needed to map PRUSS resources. A legacy loader may name this operation after an event output; opening it for mapping does not require using interrupt notifications.
5. Disable both PRUs, allow their current instructions to finish, reset the stopped cores, and invalidate any previous initialized state. The included loader bounds the stop wait to 20 ms and fails initialization if a core remains running; it does not force-reset that running core.
6. Clear any stale PRUSS notification event owned by the driver and leave its PRU-to-ARM notification route disabled. Do not enable readiness or completion interrupts.
7. Enable any required GPIO clocks and configure **all six GPIO lines as outputs driven low, even when their configured lengths are zero**, through sysfs or an included board setup path. Set each output latch low before enabling its output direction, or use an output-low operation that guarantees this ordering, to avoid driving a stale high level. Do not export or reconfigure unrelated GPIOs; preserve every unrelated `GPIO_OE` and output-latch bit.
8. Populate the PRU0 configuration with the profile identifier and six lengths from the validated file snapshot, and initialize the request/completion fields.
9. Load and start the embedded PRU0 firmware. Perform any other one-time hardware setup here.
10. Observe the command block for readiness with an absolute 100 ms monotonic-clock deadline. The implemented clock starts immediately before the load/start operation, conservatively including its code-copy cost. Bounded polling with sleeps is permitted during initialization because no pixel data is being transmitted; interrupted waits shall not restart the deadline.
11. Verify ordered `READY` with no firmware error and all sequence/gate fields zero. Report `ERROR` or expiry of the readiness deadline as an initialization failure.
12. Print the initialization success line or a precise error.
13. On success, release process-local resources and the lock while leaving PRU0 running, PRU1 disabled, all six outputs low, and the initialized hardware and configuration available to both senders.

### 9.4 Shared send sequence

1. The one-shot CLI parses its single color argument before hardware access. The UDP receiver validates its options before opening and validates each network packet before sending.
2. Open the process-local shared sender once: acquire the shared nonblocking lock and require effective UID zero.
3. Attach to the existing PRUSS UIO mapping without reset, reload, GPIO setup, or notification changes. Apply the ABI4 compatibility/readiness guard in §8.3, open `/dev/dld-quiet`, then release the lock while retaining its descriptor and the device mapping. Failed attachment releases only acquired resources.
4. For each send, reacquire the shared lock and refresh/validate the current mailbox, profile, lengths, and sequence. Submit the zero-initialized, fixed-width, pointer-free 192-byte `dld_quiet_send` ioctl structure from `include/dld_quiet.h`, using ioctl API version 1 independently of mailbox ABI4. Inputs contain RGB, retained profile/lengths, and expected previous sequence. Do not accept caller-selected MMIO addresses, masks, or loop counts.
5. The helper validates again, serializes operations, holds the single-CPU/hotplug invariant and CPSW device/runtime-PM/RTNL lifetimes, checks fixed 1 GHz and exclusive PMU availability, and checks other DMA before publication. A pre-publication rejection does not alter PRU state.
6. The kernel converts RGB to profile wire order, clears the previous grant, and publishes the new sequence with ordering. It owns the finite transaction through completion or cleanup, including if the userspace sender is killed.
7. For every nonempty bank, wait with IRQs enabled between ordered snapshots for matching `accepted_seq`, `WAIT_BANK`, and `bank_ready`, under a 20 ms gate deadline and 200-attempt cap. Establish and execute the bank window in §9.4.1. Skip empty banks completely.
8. After all banks, observe overall matching `DONE` and no error under a separate 20 ms final deadline and 200-attempt cap, with IRQs enabled between polls. The PRU performs the full reset/propagation/margin wait. This polling is outside every timed pixel stream.
9. Return structured status/diagnostics to userspace. Report success only for matching completion and no cancellation. The CLI prints its existing success line; the UDP receiver increments its local completed-send counter. Submitted failure, inconsistent result, uncertain ioctl completion, or handled cancellation after publication is critical (exit 5), requiring §9.6 cleanup and reinitialization.
10. Release the frame lock. The CLI closes process-local resources and exits; the receiver retains them for subsequent packets and closes them on exit. Successful sends leave firmware/configuration intact and all outputs low.

A recognized ioctl normally returns zero and reports execution success/failure in its structured `result` and `submitted` fields. `ENOTTY` and `EPERM` are definitive prepublication rejections and map to CLI exit 3 without cleanup. Other syscall errors leave submission uncertain: in particular, `EFAULT` may occur while copying a result after work executed. The CLI treats those errors as critical and attempts cleanup. A successful raw ioctl transaction whose result cannot be copied back does not itself become a kernel execution failure; see §9.6.

### 9.4.1 Protected bank window and completion budget

For a nonempty bank with maximum configured length `Lbank`, initial profiles use:

```text
CPU frequency       = 1,000,000,000 Hz, fixed
bank cycle budget   = Lbank × 24 × 1,200 + 600,000
maximum bank budget = 9,240,000 cycles = 9.24 ms at length 300
CPSW drain bound    = 500,000 cycles = 0.5 ms, with a finite poll cap
PMU fallback cap    = 30,000,000 loop iterations
```

The implementation derives the data portion from the shared PRU bit-cycle/frequency definitions. The 600 µs guard covers grant/PRU dispatch, end-of-bank clear and control overhead. It is an engineering allowance subject to audits and captures. Recalculate and revalidate when profile timings change. The normal IRQ-off interval also includes DMA checks, warmup, barriers, and restoration; 9.24 ms is the bank timer target, not a hard bound on every IRQ-off operation.

Before each grant, disable preemption and save/mask IRQ/FIQ on the only online CPU. Check clocks before reading peripherals. MMC command/data activity, EDMA channel-controller activity, and all three transfer controllers must be idle. Read them in two passes; an EDMA burst gap is insufficient while MMC remains active. Fully disabled controllers may be skipped only under the appliance assumptions in [quiet-window operation](docs/quiet-window.md). Transitional or unproven clocks fail admission.

With the CPSW parent held active and RTNL held, save DMACONTROL. Reject preexisting CMD_IDLE rather than claiming another owner's pause. Assert only CMD_IDLE, verify readback, and poll CPDMA IDLE within the drain bound. Preserve host-error status and fail admission. Recheck MMC/EDMA after Ethernet drains. Grant no bank until all checks pass. A transient pre-grant `EAGAIN` restores CPSW and CPU state before retrying under a 1 second admission deadline and independent 10,000-attempt cap. The initial, prepublication MMC/EDMA admission uses the same bound. CPU interrupts remain enabled between attempts, allowing ordinary storage work to finish. Drain timeout, invalid state, or failed restoration is not retried. Never retry a granted bank or extend its completion budget.

The assembly routine preloads registers and warms the exact grant/timer path before publication. It publishes the grant and loops using only Cortex-A8 CP15 cycle-counter reads, integer arithmetic, and branches. No data loads/stores, stack access, PRU/MMIO polls, cancellation reads, calls, or instrumentation are permitted in that repeated loop. CP15 is a CPU register, not a peripheral-memory timer. Require the exclusive pinned cycle event to be active, enabled, advancing, and not divided by 64. An independent finite iteration guard prevents an endless software loop if the PMU stops; expiry is critical and can exceed the normal timer target.

At the target cycle count, make exactly one ordered `bank_done` read. Any value other than the expected ordinal is critical; give that bank no further check, grace period, or retransmission. On failed granted work, request PRU stop before resuming CPSW when PRUSS remains accessible. A later diagnostic snapshot cannot reverse the failure.

Restore and verify the exact saved CPSW control word before restoring IRQ/FIQ masks and preemption. Report restoration mismatch independently and make it non-retryable. **CPSW resumes between every bank**: normal network callbacks, timer handlers, and scheduling may run only after their hardware state is restored. Holding raw CMD_IDLE across enabled intervals would race the owning driver. Final reset polling also permits ordinary CPU/network execution.

Instruction fetches and cache effects remain; this is not zero interconnect traffic. Ordinary software handlers are excluded during a granted stream, while unaccounted autonomous masters require appliance preparation. No software counter bounds a hardware bus access that never completes. Validate final module disassembly and physical waveforms (§13.8); kernel checks alone are insufficient. Initialization retains its separate 100 ms readiness deadline.

### 9.5 Concurrency and ownership

All three commands shall refuse an operation if they cannot obtain their shared exclusive lock. `dld-init` holds it through readiness; the shared sender used by `dld-send` and `dld-udp` holds it through each frame's final reset and completion handling. The UDP receiver releases it between frames but retains its descriptor. A command encountering a held lock shall fail rather than queue or interrupt the lock holder's operation. Such failure terminates the UDP receiver; it does not silently drop the selected color and continue. Stop the receiver before manual sends or reinitialization to avoid competing callers. The lock coordinates these commands; it does not detect or prevent another program from accessing PRUSS or the LED GPIOs.

The synchronous ioctl retains kernel ownership through a submitted request even if its sender is killed; its open-file/lock lifetime normally prevents a cooperating command from entering before that operation finishes. The readiness guard still rejects retained outstanding work without modification. There is no orphan flag, special wait, or automatic resend. Later commands can reuse a successful session. An explicit `dld-init` that obtains the shared lock performs full reinitialization, including stopping outstanding PRU work. Callers must not bypass this lock with independent raw hardware access.

For this iteration, an external test script shall stop the LEDscape service and then invoke `dld-init CONFIG_FILE` with the panel's local configuration. Use the service-control mechanism actually installed on the test board. The script shall ensure LEDscape has exited and will not automatically restart during the test before handing control to `dld-init`. A failed stop or initialization shall prevent the script from continuing to color sends. Service handling belongs to this script, not the CLI commands.

In production, the new driver shall completely replace LEDscape. Remove LEDscape from the production startup path, provide the matching kernel helper and runtime prerequisites, and run `dld-init CONFIG_FILE` after the required UIO/GPIO resources and local configuration are available. Start color-command operation only after initialization succeeds. `dld-init` then exits normally, leaving the PRU and configured state available for subsequent sends. Start `dld-udp` afterward when receiving the existing controller's packets; the local CLI remains usable without a resident receiver. Stop the receiver before unloading the module or handing the hardware to another application. Production service installation and recovery policy remain deployment work; the diagnostic bench did not install production startup configuration.

`dld-init`, `dld-send`, and `dld-udp` shall not scan for other PRU users, start/stop/kill services or processes, or unload a kernel driver. They trust the test script or production deployment to establish exclusive hardware use.

### 9.6 Error cleanup

After an initialization failure that took control, or a send failure/cancellation after publication, invalidate the session, disable both owned PRUs, best-effort force all outputs low, release acquired resources, and return nonzero. A later send requires successful `dld-init`. Leave notification routes disabled and transmit no black or recovery frame.

Submitted execution-failure cleanup is kernel-owned even if the sender is killed or the failure result cannot be copied back. On a failed granted bank, request PRU0 stop and invalidate the mailbox before restoring CPSW when accessible. Restore/verify CPSW and CPU masks on every window exit. Bounded cleanup then disables both PRUs, waits up to 20 ms with IRQs enabled for RUNSTATE to clear, and resets only confirmed-stopped cores. Do not force-reset a core still completing an instruction. Independently attempt each functional GPIO bank with its LED-only CLEARDATAOUT mask and bounded readback attempts. Kernel cleanup does not change directions or enable clocks behind their drivers. Record stop/low/restore failures; inaccessible hardware can prevent recovery. If a PRU cannot stop, a low readback is only an observation and a pending write may still finish later.

Userspace cleanup remains a final safeguard after a critical ioctl result or handled cancellation. Unlike kernel cleanup, the included userspace board-setup path can enable GPIO clocks and reassert the owned LED output directions after clearing their latches; it preserves unrelated output/OE bits. This is error recovery, not part of a normal send. Argument, privilege, lock, attachment, compatibility, and pre-publication busy/prerequisite failures release only acquired resources and do not overwrite or stop prior work. Busy rejection alone requires no reinitialization. Admission failure after frame publication is critical even if no bank was granted.

Failure of result copyout after a successful raw ioctl transaction leaves that successful session intact in the kernel. The CLI cannot distinguish that case from other uncertain `EFAULT` outcomes and therefore performs its conservative cleanup when it survives to receive the error. Kernel recovery-failure logging remains available when a submitted execution failure prevents successful cleanup and the caller cannot receive diagnostics.

Forcing low establishes reset, not black pixels. Pending interrupted data may latch; the previous picture need not survive. No automatic retransmission or previous-picture restoration is provided.

`SIGINT`, `SIGTERM`, and `SIGHUP` handlers set a cancellation flag without unsafe I/O. Cancellation detected by a userspace or kernel prepublication check submits nothing. A signal arriving after the final check can still be followed by publication; signal delivery is not an atomic cancellation boundary at the mailbox write. Once published, the kernel deliberately completes its finite request or cleans up failure before returning, rather than abandoning a PRU at a gate. Handled cancellation then produces userspace cleanup and exit 5. No cancellation flag is read inside the timed loop. `SIGKILL` cannot run userspace cleanup, but does not bypass kernel submitted execution-failure cleanup; successful finite work may leave a reusable session. Test these cases with ABI4 rather than assuming ABI3 sender-death behavior.

## 10. Timing and latency budget

For period `Tbit` and bank maxima `L2`, `L1`, `L0`, nominal data time is:

```text
Tdata = 24 × Tbit × (L2 + L1 + L0)
300 pixels × 24 bits × 1.2 µs = 8.640 ms per maximum-length bank
three such data passes = 25.920 ms
```

Add final `Tsettle`, bank handling, kernel guard windows, DMA admission, inter-bank Linux execution, and mailbox waits for actual completion latency. At maximum lengths, initial settle is 300 µs reset + 299 µs chain propagation + 100 µs margin = 699 µs. Nominal data-plus-settle is therefore 26.619 ms before other overhead. The initial bit rate is approximately 833.33 kbps. Arithmetic targets do not substitute for measured edges.

Each maximum-length bank has a 9.24 ms kernel timer budget, plus at most 0.5 ms normal CPSW-drain allowance and admission/control/restoration overhead (§9.4.1). Record actual IRQ-off, drain, and stream durations. Gate and final-completion waits retain separate 20 ms policies. Initial and per-bank DMA admission each allow up to 1 second with IRQs enabled between attempts; scheduling can delay observation or syscall return. These admission waits cannot extend an already-granted bank. Initialization retains its 100 ms readiness deadline.

The former acceptance-to-`DONE` requirement of less than 30 ms is withdrawn for the protected path. PRU bank gates intentionally allow Linux/networking to run between streams. Measure acceptance-to-final-`DONE`, first-to-last source edges, ioctl duration, and command duration separately. Do not infer a hard end-to-end deadline from bank bounds. The resident shim removes process startup and remapping overhead and coalesces queued packets (§4.5); sustained 20 Hz reception/output and packet loss still require target measurements.

For equal 300-pixel banks, nominal data-only first-to-last bank-completion skew is 17.28 ms. Enabled inter-bank gaps add to it; reset/propagation and shorter strings affect visible updates. Sequential skew remains accepted. No added latch synchronization or synchronization across all 72 panels is required.

Shortening a string reduces bank data time only when it reduces its bank maximum; it reduces `Tchain` only when it reduces the panel maximum. Empty banks receive no grant/window. All-disabled sends still await reset plus margin with zero chain delay. Success must never precede matching overall completion after that hold.

## 12. Non-goals for the current utility

The current utility, including the legacy UDP shim, does not provide:

- independent colors per string;
- independent colors per pixel;
- general-purpose animation beyond the two UDP status flashes in §4.5, dithering, interpolation of incoming colors, gamma correction, or brightness limiting;
- TCP reception or complete LEDscape/OPC feature emulation beyond §4.5;
- packet sequencing, acknowledgments, or automatic retransmission;
- production boot-service installation or automatic driver recovery;
- independent firmware identity/liveness verification on each send;
- competing-process detection or automatic service management inside the CLI commands;
- universal quiescence of every autonomous bus master or portability to an unexamined kernel/appliance;
- a guaranteed whole-frame/UDP response deadline;
- dynamic pinmux changes;
- support for arbitrary BeagleBone pins;
- support for string lengths above 300;
- mixed pixel profiles within a panel;
- arbitrary user-supplied waveform timing values;
- automatic blacking of disabled strings;
- automatic retry after a malformed physical waveform.

## 13. Acceptance tests

This section defines the checks and their limits, not a claim that every production measurement is complete. The [final September 6 report](docs/validation-20260906.md) records completed software, lifecycle, header-waveform, and endurance evidence. Actual panel color/latch checks, first/final-pixel DIN correlation, analog margins, and production qualification remain outstanding.

### 13.1 Argument parsing

The host test suite shall verify parsing independently for the two one-shot commands:

- `dld-send` accepts every valid six-digit hexadecimal color;
- `dld-send` accepts optional `0x` and `0X` prefixes;
- `dld-send` rejects too few or too many hex digits and nonhex characters;
- `dld-init` accepts each supported profile and exactly six integer lengths from 0 through 300;
- `dld-init` rejects malformed JSON, missing/duplicate/unknown fields, unknown profiles, wrong value types, negative or oversized lengths, fractional values, and arrays shorter or longer than six elements;
- `dld-init` reports an unreadable file without touching hardware;
- both commands reject missing or extra arguments before touching hardware, including configuration or length arguments passed to `dld-send`.

For `dld-udp`, verify invalid flags, numeric addresses, and port bounds before
sender attachment, and `--help` without device access. Test the pure OPC parser
over header/length boundaries, every channel/command, first-pixel RGB, and
trailing bytes. Exercise the real receiver over loopback with a fake sender:
IPv4/IPv6, malformed packets, repeated colors, 64-packet batches, bursts,
slower-than-20-Hz simulated sends, exclusive bind, idle termination, and fatal
send/cancellation behavior. Test the shared sender with mocked OS boundaries
for retained resources, per-frame locking, fresh initialized configuration,
sequence wrap, rejection/cleanup, and existing CLI behavior. These software
checks do not establish native 20 Hz output, network loss, or physical timing.

Verify both status flashes are enabled by default and independently disabled
by their flags. Check initial black, full primary, and final black; elapsed-time
selection with fast and slow synchronous sends; strict inactivity expiry and
recurrence; and activity from valid, malformed, and unsupported datagrams.
Verify valid packets interrupt flashes only between sends, invalid packets
reset inactivity without interrupting an active flash, and shutdown or sender
failure follows the existing lifecycle contract. Keep packet-only regression
tests with both flashes disabled. Software timing checks do not establish
the flash's appearance or cadence on the installed panel.

### 13.2 Pin mapping and exact lengths

For each length array, put it in a valid panel configuration file, run `dld-init CONFIG_FILE` followed by `dld-send COLOR`, and verify the physical output:

| Configured lengths | Only output allowed to pulse |
|---|---|
| `[300, 0, 0, 0, 0, 0]` | P8_8 |
| `[0, 300, 0, 0, 0, 0]` | P8_10 |
| `[0, 0, 300, 0, 0, 0]` | P8_12 |
| `[0, 0, 0, 300, 0, 0]` | P8_14 |
| `[0, 0, 0, 0, 300, 0]` | P8_16 |
| `[0, 0, 0, 0, 0, 300]` | P8_18 |

Initialize with all six lengths 300, send a color, and verify that:

- P8_8, P8_10, and P8_18 transmit simultaneously during the GPIO2 pass;
- P8_12 and P8_16 transmit simultaneously during the GPIO1 pass;
- P8_14 transmits during the GPIO0 pass;
- inactive groups are low;
- the three passes occur in the specified order.

Test unequal lengths within one bank, including `[300, 180, 0, 0, 0, 1]` for GPIO2. Verify exactly 300, 180, and one pixel word on the corresponding pins, with no pulse after each pin finishes and uninterrupted timing on its longer neighbors. Also test equal endpoint lengths, each pin at length one, zero-length neighbors, the maximum length, and all-zero configuration.

### 13.3 Color order

For every supported profile, verify RGB primaries and an asymmetric color with a decoder or logic analyzer, and confirm the resulting colors on the actual panel. Expected wire bytes must follow the selected profile. For a GRB profile, the minimum patterns are:

| Input RGB | Expected wire bytes |
|---|---|
| `FF0000` | `00 FF 00` |
| `00FF00` | `FF 00 00` |
| `0000FF` | `00 00 FF` |
| `123456` | `34 12 56` |

Each wire word must repeat exactly the configured length on each enabled pin. For example, an RGB profile sends input `123456` as bytes `12 34 56`; a GRB profile sends `34 12 56`; either BGR variant sends `56 34 12`. Use these as examples of profile ordering rather than assuming every pixel family has the same order.

### 13.4 Waveform

At the first pixel's DIN after the level shifter and wiring, and at the physical header pins for comparison, measure:

- the selected profile's bit period from consecutive rising edges, and zero/one high and low durations; the initial targets for both LED types are 1,200 ns per bit, 350/850 ns for zero high/low, and 700/500 ns for one high/low;
- no unintended low interval long enough to reset a still-active string inside its configured pixel stream;
- correct pixel-boundary timing when one or more pins leave the active mask;
- the full `Tsettle` hold after the final bank's successful clear/readback, including the profile's reset, chain-propagation bound, and safety margin;
- `dld-send` reports success and exits only after that hold, so every configured pixel has had sufficient reset-low time to latch;
- no activity on disabled LED pins;
- no activity on unrelated GPIO bits caused by the utility.

Document measured minimum/maximum durations, sampling resolution, measurement uncertainty, test conditions, and any profile adjustments. The completed diagnostic header testing uses ±50 ns for zero/one highs, in-frame lows, and rising-edge bit periods; those limits were not widened after failures. Low intervals that include the final reset are not ordinary in-frame lows. Installed-pixel acceptance limits still require qualification against the actual hardware; the shared starting waveform does not establish those limits by itself. Record final profile parameters and their validation in source comments. Verify the 5 ns nominal adjustment capability from the final assembly, including any extra-cycle delay path.

For completion validation, correlate the final source edge, PRU `DONE` publication, and the host's completion observation with the last configured pixel's DIN on representative longest strings. Test instrumentation may mark these boundaries outside the timed pixel stream without enabling PRU-to-ARM interrupts. Verify that the last pixel's required reset-low interval has elapsed before `DONE`. Test length one, length 300, unequal lengths, a longest string in an earlier bank with a shorter final bank, and all-zero configuration. Check the delay calculation and upward cycle rounding separately from hardware captures.

### 13.5 Duration

For each profile, record bank data duration, protected timer/IRQ-off/drain cycles, gate gaps, acceptance-to-final-`DONE`, and command latency. At all lengths 300, compare measured streams with nominal 8.64 ms per bank and verify each granted bank finishes within its 9.24 ms timer target. Check the 20 ms gate/final policies separately from the 1 second DMA admission policy. No acceptance-to-`DONE` 30 ms requirement applies.

Test shorter/unequal lengths, all-disabled configuration, and a longest string in an earlier bank. Verify propagation allowance follows the panel maximum, stream length follows each bank maximum, and `DONE` follows all of `Tsettle` independent of scheduling gaps.

### 13.6 Endurance

The original single-probe oscilloscope procedure below remains a repeatable stretched-high diagnostic. The completed September 6 bench instead recorded six digital channels at 500 MS/s and analyzed complete pulses, in-frame lows/periods, wire contents, counts, and bank ordering within captured intervals. Its final protected run covers 18,257.095062016 seconds, 4,452,206,525 complete pulses, and 663,562 complete channel frames with no observed violations. Fourteen full phases completed; the final black phase was shortened for handback. Acquisition gaps remain unobserved, and this result is not a claim that the single-probe trigger stayed armed without gaps for several hours. Detailed phase coverage and the earlier failed runs remain in the [bench report](docs/validation-20260906.md).

For the single-probe procedure, connect an oscilloscope to a selected LED data pin, record its GPIO bank and measurement location, and run `dld-init CONFIG_FILE` with the panel's profile and all six lengths 300. Repeatedly invoke `dld-send` with the same color for each phase below. Start each invocation after the previous one returns successfully, with no deliberate inter-command delay; stop the send loop on a command failure.

| Phase | Command repeated for several hours | Nominal high time | Positive pulse-width trigger |
|---|---|---:|---:|
| All zero bits | `dld-send 000000` | 350 ns | Greater than 400 ns |
| All one bits | `dld-send FFFFFF` | 700 ns | Greater than 800 ns |

These colors produce all-zero or all-one wire data regardless of the selected byte order. Both phases retain the 1,200 ns nominal bit period. The thresholds allow 50 ns and 100 ns above the respective nominal high times. The all-one phase exercises the longer high-time path; both phases detect high pulses stretched beyond their selected limit. These are diagnostic trigger limits, not complete LED input-timing acceptance specifications.

Use a positive pulse-width greater-than trigger, with a trigger voltage appropriate to the probed signal. Arm the scope to retain a qualifying event for inspection, using normal or single acquisition as supported. Confirm the trigger setup works before beginning the timed run, then clear its history. Stop sending, change the width threshold, and clear/rearm the trigger before switching phases so ordinary one pulses are not counted against the zero-phase limit.

For each phase, record the actual monitoring duration, pixel profile, pin/bank, measurement location, trigger voltage/width settings, send count or achieved cadence, command failures, and any captured violations. A qualifying capture is a test failure to investigate; preserve the waveform. If no violation is observed, report that result for the actual pin, settings, and monitoring interval. The same pair of runs can be repeated on other GPIO banks and panel types, moving one probe between runs; do not claim coverage for untested outputs.

First-pass acceptance for each monitored run is no observed positive pulse above its phase's threshold over several hours, with no command failures, kernel warnings, or observed stuck-high output. Record oscilloscope acquisition gaps if relevant; a clean run does not establish gapless detection. Some pulse-width triggers qualify only when the pulse falls, so separately note a signal that remains high. Check the actual instrument's trigger behavior; see the [Tektronix pulse-width trigger description](https://www.tek.com/en/support/faqs/tds1000-and-tds2000-series-scopes-where-trigger-point-when-pulse-width-trigger-used-and) and [Keysight 54620/40-series trigger documentation](https://www.keysight.com/lk/en/assets/9018-40677/user-manuals/9018-40677.pdf).

This test does not establish that shorter pulses, low intervals, rising-edge spacing, bit counts, or complete frames are correct. Keep those checks in the shorter waveform and functional tests (§§13.1–13.5, 13.7–13.8). Repeated identical frames also cannot expose every dropped, duplicated, or stale-color request. Alternating-color visual inspection is not required for this endurance test. The several-hour scope runs replace the previous mandatory 24-hour visual test and 10-million-bit logic-analyzer capture criterion.

Repeat the protected physical checks under deliberate CPU, DDR, Ethernet, and selected storage activity. Verify admission waits or rejects safely and every granted stream meets the selected physical limits. Record load, achieved rates, failures, and observed intervals; preserve failed captures. Unprotected captures are comparison evidence, not protected-path qualification.

### 13.7 Initialization and repeated sends

Verify the established CLI behavior and protected lifecycle:

- Invalid input and missing/incompatible/invalid mailbox state fail before publication with the specified codes and no mutation. Busy includes `WAIT_BANK`, `RUNNING`, and unequal sequences, including stale-status publication intervals.
- Initialization makes all six pins output-low, including disabled pins, preserves unrelated bits, emits no data, and observes zero ABI4 handshakes plus `READY` within 100 ms.
- Healthy idle latched colors survive initialization; interrupted-frame recovery need only establish low/reset. No black or recovery frame is sent.
- Repeated sends use retained configuration without reload/restart/GPIO setup. File edits alone do not change it; reinitialization does. Working masks/counters preserve configured lengths.
- Each nonempty bank waits for its fixed ordinal grant, empty banks are skipped, and stale grants/done cannot satisfy a new request. Test sequence wraparound in a focused protocol test.
- A stopped PRU with a valid ready mailbox permits publication but produces bounded critical gate/completion failure, without identity probes. A stopped PRU retaining busy state is rejected before publication.
- All-disabled sends issue no data/grants, wait reset plus margin, and report `groups=0`. Successful sends leave outputs low and matching, reusable `DONE`.
- Shared-lock contention leaves the active command untouched. The kernel mutex separately serializes ioctls. Device/module lifetimes remain held through the operation.
- Cancellation detected at a prepublication check submits nothing. A signal arriving after the final check may be followed by publication. Kill a real sender during controlled protected work and verify any submitted request completes every gate or performs failure cleanup. Successful completion is reusable; failure invalidates the session and records stop/low results. Do not assume userspace handlers run for `SIGKILL`.
- Handled post-publication cancellation gives critical cleanup/reinitialization. A failed bank observation stays failed even if a later diagnostic snapshot changes; there is no grace check or retry.
- Firmware errors, final mismatch/timeout, PMU guard failure, and CPSW restoration failure take critical cleanup. Exercise kernel cleanup for submitted execution failures even when result copyout or userspace survival is unavailable. Separately verify definitive `ENOTTY`/`EPERM` preserve the session and uncertain syscall errors trigger the surviving CLI's conservative cleanup.

Verify the external handover stops LEDscape and competing senders before initialization and prevents restart during testing. Production startup provides the module, runtime prerequisites, and successful initialization before colors. CLI commands perform no process scans or service management.

### 13.8 Kernel quiet-window validation

Inspect final module disassembly: repeated waits have only CP15 reads, arithmetic, and branches; the warmed grant path has no intervening C call or unexpected stack/data access; exactly one bank completion is read. Check finite fallback, counter wraparound, disabled/divided/stopped PMU rejection, fixed frequency, and maximum/unequal/zero budgets. Measure PMU behavior and nominal PRU timing on the actual Cortex-A8.

Verify every controller read is clock-qualified within a preemption/IRQ/FIQ-excluded batch. Exercise fully disabled, functional, transitional, and active MMC/EDMA states without touching disabled blocks. Transient pre-grant busy may retry only after restoring CPSW/CPU state and within its bound. Post-grant failures or restore mismatches never retry. Check the two-pass MMC/CC/TC predicate and TC reserved-bit handling.

Verify CMD_IDLE assertion and exact CPSW restoration by readback. Reject an already-paused controller without claiming it; retain first host-error status. CPU handlers resume only after hardware restoration. Check Ethernet and MMC operation after success, admission rejection, and injected failure. No per-bank descriptor teardown, event clearing, or interface restart is allowed.

Verify clock-qualified PRU stop/reset and GPIO-low cleanup on submitted failure, including after the first bank and inaccessible-controller diagnostics. Never force-reset a core still reporting RUNSTATE. Check unrelated GPIO preservation and report recovery failures separately.

Use physical captures under normal and matched deliberate loads to determine whether protection eliminates observed GPIO0 anomalies. Successful ioctls, idle status, clean assembly, and software tests cannot prove waveform correctness or universal bus-master silence.

## 14. Future work

### 14.1 Broader kernel integration

The loadable bank-gated helper is required current functionality (§9.4.1). Future integration may replace fixed-address/single-CPU assumptions with driver-owned pause APIs, runtime-PM ownership for every peripheral, and support for other kernels/CPU policies. These changes require new timing/restoration validation and must not silently weaken admission.

### 14.2 Network protocol and pause policy

Current sends pause and restore CPSW separately for each bank. Command-idle preserves descriptors but incoming packets during the pause may be discarded. The current legacy shim (§4.5) coalesces bounded batches and intentionally preserves the unacknowledged OPC/UDP format, without sequencing or retry. Measure its cadence and packet loss with the existing controller before deployment. A future reliable protocol may add completion acknowledgments and retry coordination; acknowledge only after overall completion and network restoration. Keeping raw CMD_IDLE asserted while Linux network callbacks run is not an acceptable extension; a longer pause needs integration with the owning driver.

### 14.3 Other appliance configurations

The reference board's MMC/EDMA admission, single CPU, disabled PRU1, no swap, `tmpfs` runtime/logs, user-LED preparation, and PIO-only USB are current assumptions. USB/gadget services remain intact. Read-only inspection found no bound McASP/SPI/ADC/LCDC client or active SGX device; this is deployment evidence, not a universal invariant.

For a different kernel/appliance, enumerate and exclude or coordinate additional autonomous masters: USB DMA, audio, LCDC, SGX, SPI/ADC DMA, timer-triggered EDMA, or another PRU. Prefer device/driver ownership and structural elimination of unused masters. An idle snapshot cannot prove an unaccounted external event will not start work during a bank. Do not freeze the root filesystem or globally clear/disable unrelated EDMA as a shortcut.

### 14.4 Future reliable UDP protocol

The current `dld-udp` shim already reuses the initialized PRU and shared sender resources (§4.5). The earlier proposal below is a possible separate controller/protocol revision, not the legacy packet format or a requirement for this shim. Process reuse alone does not establish the desired 50 ms end-to-end bound: scheduling, queueing, Ethernet pause/recovery, and admission policy must be measured and designed for it. The current 1 second admission policy makes no such guarantee.

Suggested packet fields:

```c
struct udp_led_command {
    uint32_t protocol_version;
    uint32_t sequence;
    uint32_t rgb;
};
```

Candidate behavior for that future protocol:

- monotonically increasing sequence numbers;
- duplicate suppression;
- completion acknowledgements;
- sender retry after timeout;
- validation before entering the quiet window;
- coalescing of queued color updates so stale intermediate colors are dropped;
- retain the separation between panel profile/length configuration and high-rate color commands: only `dld-init` reads persistent local configuration, and either sender uses the initialized copy in PRU memory rather than adding an independent enable mask to color packets.

### 14.5 Disabled-string blackout semantics

Extend the enable/disable configuration established by `dld-init` with automatic blackout of newly disabled strings.

When a string changes from enabled to disabled:

1. send one black frame using that string's previous nonzero configured length;
2. wait for reset/latch;
3. set its configured length to zero so it is absent from subsequent color-update masks.

When a string changes from disabled to enabled, assign its new nonzero length and include it in the next normal color update.

This configuration operation need not meet the real-time color-update deadline.

### 14.6 Instrumentation and retry

Add counters and diagnostics for:

- PRU execution duration;
- bank start and completion timestamps;
- end-of-bank clear-readback retries;
- longer-term statistics for current quiet-window and DMA-drain diagnostics;
- timeout and abort causes;
- last completed sequence number.

Current admission may retry only before granting that bank and within its bound. A future recovery policy may deliberately reinitialize and retransmit the entire frame from pixel zero when safe. That policy is not part of these commands: submitted critical failure requires explicit reinitialization and never automatic frame retransmission.

### 14.7 `DATAOUT` comparison

Only if the isolated SET/CLEAR implementation still glitches, implement a controlled A/B test using preserved full-word writes to `GPIO_DATAOUT`.

The `DATAOUT` version must preserve every non-LED bit in the bank and must never write a bare LED mask or zero to the whole bank. GPIO1 is especially sensitive because the bank contains non-LED board functions.

Adopt `DATAOUT` only if a long capture shows a materially better worst-case pulse-width distribution. The default and preferred implementation remains `SETDATAOUT` / `CLEARDATAOUT`.

### 14.8 Production acceptance

Before production deployment, repeat the endurance and waveform tests with:

- the installed pixel family, physical byte order, reset/propagation bounds, and electrical margins qualified as required by §§6.1 and 13.3–13.4;
- the kernel quiet-window driver enabled;
- CPSW DMA idle during streaming;
- documented appliance assumptions verified and additional autonomous masters excluded or coordinated;
- worst-case expected Ethernet traffic immediately before a command;
- repeated commands at the maximum intended update rate;
- watchdog, timer, and network-recovery monitoring.
